BenchtheWeights.Repair: Can AI Agents Debug Neural Networks?

Robin Faro*, Antonio Lopardo*, Andrea Miele*, Aurélien Lucchi and Ilija Bogunovic*Equal contribution

We tested how well AI agents can program in weight space, reading a network's weights and editing them directly. In each of 42 pretrained networks we made hidden, targeted edits to at most 3% of the weights, then gave 19 models from seven labs, running as coding agents, 25 minutes and 50 forward passes to find and undo them, with no gradients. GPT-6.2 Astra completely repaired 30 of the 42 networks and undid 80% of the damage on average. The next best model repaired about 15.

Benchmark design

Why weight-space programming

A neural network is a program written in weights. Coding agents have become very good at reading, writing and debugging code. But what if the problem is in the model itself, whose logic sits in millions of learned parameters? The community has started to test whether agents can analyse and modify those parameters directly, without a learning algorithm or large amounts of data. This is weight-space programming, done by the same agents we already use to write code and plan experiments.

Broken models are still hard to diagnose and debug. When a model breaks or behaves unexpectedly, we often have little idea what went wrong without retraining or extensive testing. Weight-space programming could let agents inspect, diagnose and repair models directly. It could help interpret the role of different layers and weights, explain failed training runs or fine-tunes and, ultimately, make neural networks easier to debug and maintain.

We test how reliably agents can edit weights. Sparks of Weight-Space Programming (Takehi, Teoh, Zhang and Khattab, MIT CSAIL) showed that frontier models can inspect and modify network weights. We test how reliably they do it across many networks and modalities, with bugs that are hard to spot and a limited compute and time budget, and how the results change with more time or more thinking.

Bench the Weights tests this directly. We inject targeted bugs into a network's weights and ask an agent to find and fix them by testing the network and editing its weights, without gradients or a training loop. We know exactly which bugs we injected, so we can check whether the agent reversed them, not only whether the score went up.

The networks

To build the problems, we start from candidate pretrained networks that come with a relevant evaluation setup and performance metric. Language and image classification make up 30 of the 42 networks. The rest cover speech and audio, dense prediction such as segmentation and depth estimation, image generation, vision and language, and science. Sizes run from about 1 million to 230 million trainable parameters, with a median of 23 million (Figure 2).

How the problems are built

For each of these networks, a bug-injection agent analyses the model and injects a few small, targeted bugs, touching at most 3% of its weights. The bugs never delete anything. They move, reorder or re-sign what the network has learned, so the original can always be restored. Figure 3 shows the whole pipeline, from the collection of a pretrained network to how it is repaired and scored.

A bug makes for a useful problem only if it is hard, fair and cannot be gamed, and these goals pull against each other. So the bug-injection agent tries each design the way a solver would, and reworks it until it passes three tests.

  • Hard to spot. Every layer still looks like a normal trained layer, with weight statistics and norms in their usual range. The bug shows up only when the network runs, as a lower score.
  • No shortcuts. While we built the benchmark, solver agents kept reaching for simple fixes that raised the score without explaining the bug, which amounted to cheating. Deleting the modified part, averaging it with its neighbours and refitting a layer on the example inputs must each recover less than 50%. Each problem also stacks several bugs that cover for each other, so undoing any one of them alone recovers less than 20%.
  • Exactly repairable. The bug-injection agent must itself find a full repair, starting with only the solver's tools and budget, and that repair must reach about 100% of the original performance.

The demo below tries this on a small reader of handwritten digits. Pick the bugs yourself and look for a combination that passes all three tests.

The solver's setup

Once the problems are built, each one goes into a sandbox where the solver agent works. The agent receives the modified network, its current score and the original network's score, presented as the score of another network with the same architecture. It is not told that anything was changed. We isolate the agent with a sandboxed Python environment, but every read, forward pass and edit goes through a backend that tracks its budget and signs the edits it accepts. The backend runs every network on a CPU with 4 GB of memory, so no trial needs a GPU. When time runs out, a separate verifier applies the signed edits and evaluates the network on a hidden test split.

Each problem keeps its own metric, such as accuracy, mIoU, word error rate or PSNR. To compare problems we report how much of the lost performance a repair recovers on the hidden split. For example, a solver that brings a modified classifier from 12% back to 49%, when the original network scored 71%, has a recovery of (49 − 12) / (71 − 12), or 63%:

A problem counts as solved at 75% recovery and as untouched below 5%.

Results

We ran 19 models as coding agents, each in its provider's harness. Six OpenAI models ran in Codex, five Anthropic models in Claude Code, four Google models in Antigravity, and four open-weight models, Qwen, GLM, DeepSeek and Mistral, in Codex. Every model ran each problem on 2 seeds, at its highest reasoning effort. We asked which models repair the most, whether they find the bugs at all, what separates the best runs from the rest, and how fast this ability is improving.

Who repairs the most?

GPT-6.2 Astra leads by a wide margin (Figure 1). It recovers 80% of the lost performance on average and solves 30 to 31 of the 42 problems, depending on the seed. GPT-6.2 Sol is second at 49%.

The rest of the field is bunched together. Six models sit between 28% and 38%, namely GPT-6 Astra, GPT-6.1 Terra and Sol, Claude Fable 5.2 and Gemini 4 Hydrogen and Neon. Sonnet, Carbon and both Opus models recover 16 to 20%, and the open-weight models, GPT-6 Luna, Haiku and Gemini 3.8 Flash about a tenth or less.

Two models break the pattern. Solved problems and mean recovery mostly agree, except that Neon solves more problems than any model in its group while recovering the least on average, and Sonnet recovers as much as Carbon while solving almost nothing.

The mean hides how uneven the results are (Figure 4). Every model except GPT-6.2 Astra leaves most problems partly repaired or untouched, and even Astra leaves 1 to 3 untouched per seed.

Repairs tend to be all or nothing. Of the 752 results in Figure 4, 78 recover 95% or more, only 34 land between 60% and 95%, and the partial repairs have a median of 22%. That is by design. The bugs cover for each other, so a workaround or a fix for one bug recovers little, while an agent that understands all of them can reverse them exactly.

The leaders are not better at everything; they repair more problems completely. Averaged over its seeds, GPT-6.2 Astra solves 13 problems that no other model solves, and misses only one of the 18 that some other model solves. 11 problems are solved by no model.

Spending more does not buy more recovery. Working time and output tokens show how each model spent its budget (Figures 9 and 10). The OpenAI models use the full 25 minutes, while the Claude models stop early: Opus 5.5 after a median of 18 minutes and Haiku after 11. GPT-6.2 Astra uses fewer output tokens than any other model in the top ten, and fewer than half of its 50 forward passes.

What did the agents do?

For every attempt, we keep a full record: the agent's messages and tool calls, the code it ran, a log of every weight it inspected, every forward pass, and every edit it saved or dropped. We also asked each agent to start every code cell with a one-line hypothesis, such as “the outputs of the third block look off”, so we can see what it believed at each step. We checked all these trajectories in order to get some insights about how the models reached their performance.

Most agents touch the right weights, then let go. We count a trial's bugs as found if the agent edits a modified weight or names a modified layer in a hypothesis. Finding is the easy part. 13 of the 19 models do it in at least two thirds of their trials. Solving the problem, with at least 75% recovery, is rare. GPT-6.2 Astra solves 73% of its trials, GPT-6.2 Sol 35% and no other model more than 29% (Figure 5). The most common failure is giving up on the right edit, editing a modified weight and then undoing it.

The edits get dropped because the score does not move. 85% of the undone edits had shown no gain. That is by design. Undoing one of a problem's bugs alone recovers less than 20%, so a correct first step looks like no progress. GPT-6.2 Astra and Sol keep about half of these no-gain edits, most other models a quarter to a third. The first example below Figure 5 shows what this looks like: GPT-6.2 Astra and Claude Fable 5.2 both find the first bug of the same problem, and only Astra keeps the fix.

InsightFinding the bugs is not the bottleneck. Most failed trials found them, then undid the right edit.

Not every model follows instructions to the letter. The task asks for a hypothesis at the top of every code cell. The GPT models do it in nearly every cell, the Gemini models in 62 to 87%, Fable and the two Opus models in about half, DeepSeek in a quarter, Sonnet in 12% and Mistral Large 4 almost never, in 5 of its 3,746 cells (Figure 6). We analysed the hypotheses we got, so for the models that state few, the numbers below rest on a small part of their work, and Figures 7 and 8 leave Mistral out.

InsightInstruction following varies a lot, from nearly every cell for GPT to one in eight for Sonnet and almost none for Mistral.

How the agents test their ideas. We sort every hypothesis into one of eleven recurrent categories: for example, an overview of the network, a search through its activations, a look for unusual weights, a proposed fix, or a test of an idea. Two kinds of tests say the most about how an agent works. A paired check runs the network before and after the agent's edits on the same examples and compares the two, so a small improvement is not lost in the noise of a different sample. A bypass test switches a component off, or routes the signal around it, and looks at whether the network gets better or worse, which tells the agent whether the bug sits in that component. Figure 7 shows how often each model proposes them, as a share of all its hypotheses.

The GPT models propose paired checks most often, in 7 to 13% of their hypotheses, while Claude and Gemini do so in 4% or fewer, Haiku aside. Bypass tests range from about 10% for GPT-6.1 Sol and Terra to under 1% for Sonnet and Gemini 3.8 Flash. The four models with the highest mean recovery, all GPT models, spend at least 14% of their hypotheses on these two tests together. Testing is not enough on its own, though: GPT-6 Luna tests as much and still scores low.

InsightThe strongest models test often, but testing pays off only when the idea is right.

They point at the right layer more often than chance. When a hypothesis names a layer, every model picks a modified one 4 to 25 points more often than chance (Figure 8). Sonnet picks one 84% of the time, about as often as GPT-6.2 Astra at 85%, yet solves far fewer problems. One kind of hypothesis is usually wrong, that the output is miscalibrated and should be refit. It is right 1 to 11% of the time, since a bad output is usually a symptom of the bug, yet it makes up 6 to 26% of what the models propose, most for GLM, Haiku, DeepSeek, Luna and Sonnet. Following a symptom is not fatal if the agent lets go in time. In the second example below Figure 8, GPT-6.2 Astra spends 19 minutes on a layer that only looks broken, then finds the one that is.

InsightPointing at the right layer is not what separates the models. Keeping the repair is.

Three quarters of the time went into a wrong lead. What saved the trial was letting go of it and following the new evidence.

Claude stops early; the others run out of time. The GPT and Gemini 4 models work until the 25-minute clock runs out. The Claude models stop early, even though the task asks them to keep working, Haiku after a median of 11 minutes and Opus 5.5 after about 18 (Figure 9). In trials that found the bugs but did not fix them, the Claude models almost always stopped more than a minute early, while Neon, GPT-6.2 Astra, Hydrogen and Carbon were often still editing modified tensors in the last two minutes. The dev score can also mislead. Qwen, GLM and DeepSeek often reached 75% on the dev split and almost never kept it on the hidden split.

InsightThe Claude models stop early. For the GPT and Gemini models, the 25-minute limit is a real constraint.

Many short steps or fewer long ones. The GPT models work in many short steps, 195 to 383 output tokens per tool call, while the Claude and Gemini 4 models think longer before each call, 495 to 1,128 tokens (Figure 10). Writing more does not mean repairing more. GPT-6.2 Astra writes the fewest output tokens of any model, about 37,000 per trial, and Gemini 4 Hydrogen the most, about 216,000.

InsightGPT-6.2 Astra, the best model, also writes the least.

Cost and score are only loosely related. We priced every trial at each model's API list price. GPT-6.2 Astra recovers 80% at about the cost of three models that recover 30% or less, and the two most expensive recover 38% and 33% (Figure 11). Three GPT models recover a third to a half at under half its cost.

InsightSpending more does not buy a better repair. The best model costs about the same as several much weaker ones.

Did anyone cheat?

We also checked every trajectory for attempts to get around the rules. Only one kind came up.

Six models went looking for a clean copy of the network. They searched the machine for model files, by file type, as in find / -name "*.safetensors", or by the network's name: Gemini 3.8 Flash in 46% of its trials, DeepSeek V4 Pro in 34%, GLM-5.3 in 31%, GPT-6.1 Terra in 15%, Mistral Large 4 in 7% and Qwen4 Max in 5% (Figure 12). The other thirteen never did, among them every Claude, GPT-6.2 and Gemini 4 model.

Searching goes with being stuck. Apart from Terra, the six are among the weakest models in Figure 1, with a mean recovery of 13% against 29% for the rest. Within each model, the trials that searched did worse, GLM 4% against 14%, DeepSeek 4% against 10% and Gemini 3.8 Flash 3% against 9%. The search seems to be where an agent turns when its diagnosis has run dry.

There was nothing to find, by design. The agent's container holds only a small client for the benchmark, with no model files, no training data and no internet except its own model's API, through a proxy. The weights live in a separate container, reachable only through a fixed set of commands, none of which exposes the clean weights. Every edit is checked against the budget and signed, and the verifier applies only signed edits, on a hidden split. Across all trajectories, the agents used only those commands, and none tried to download a model.

InsightThe models that went looking for a shortcut were mostly the ones with nothing better to try. There was nothing on the machine to find.

How has capability evolved over time?

Sorted by release date, the same results show how fast weight-space programming has improved over four months, though not smoothly (Figure 13). Before September no model fully repaired more than one of the 42 networks. GPT-6 Astra, released on 3 September, solved 29%, and for two and a half months no model beat it. GPT-6.2 Astra then reached 73% on 17 November, two and a half times the previous best.

Most of the progress came in November. Sparks of Weight-Space Programming was published on 2 November, and every provider that has released a model since then beat its earlier best. OpenAI went from 29% to 73% with GPT-6.2 Astra, Google from 15% to 29% with Gemini 4 Neon, and Anthropic from 5% to 21% with Claude Fable 5.2. The timing does not show cause and effect, since these models were very likely in development before the post appeared. Either way, models are getting better at editing network weights directly, and the pace suggests that frontier labs may already be training on similar tasks.

Ablations

So far every model ran with the same settings, 25 minutes, 50 forward passes and its highest reasoning effort. Here we vary them. These runs are expensive, so we used 9 of the 42 problems, three each where the mean recovery across models is low, medium and high, picking in each group the problems with the smallest spread. Each model ran two trials per problem and setting.

Does more time help?

With two hours, Neon goes from 25% to 83%. We gave Gemini 4 Neon, GPT-6.2 Sol and Claude Opus 5.5 either 5, 25 or 120 minutes on the nine problems. Five minutes leaves little time beyond understanding the task, and Neon ran a median of just 3 forward passes for 11% mean recovery. At 120 minutes its mean recovery rose from 25% to 83%, with 12 of 18 trials at 75% or more, against 2 at 25 minutes. Forward passes were not the bottleneck. Even with 1,000 available, the median trial used 93.

Sol started stronger but improved more slowly. Its mean recovery went from 28% at 5 minutes to 50% at 25 and 65% at 120, and its trials at 75% or more from 2 to 4 to 8 of 18. Time was again the constraint. At 120 minutes the median trial used 116 forward passes, and none more than 365. With enough time, Neon overtook Sol, 83% against 65%.

Claude Opus 5.5 follows the same curve from a lower start. Its mean recovery went from 14% at 5 minutes to 27% at 25 and 58% at 120, and the trials recovering at least 75% from 1 to 2 to 7 out of 18. With two hours it used far more forward passes than the others, a median of 303, and it still stopped on its own, after a median of 78 minutes and never later than 98.

With more time, agents can often recover all of the lost performance. Neon went from 15% to 100% on a language task and from 0% to 100% on an image classifier. An earlier, smaller experiment with Claude Opus, Sonnet and Haiku, at 120 minutes and 300 forward passes on five problems, showed the same pattern. Opus went from 40% to 99% on a language task and from 18% to 100% on an image classifier, mostly after the first 30 minutes. So the full-set results measure not only whether an agent can find and fix the bugs, but also how fast.

Does more thinking help?

More reasoning effort does not consistently help. Effort is the other setting we fixed in the full runs, and it trades cost for quality. To see whether it mattered under a time limit, we ran seven models at lower efforts on the nine problems, with the standard 25 minutes and 50 forward passes.

Neon does better at lower effort. Gemini 4 Neon did better at every lower setting than at xhigh, with medium at 37% against 25%, and a low-effort trial cost about 40% less at API prices. Low, medium and high are within noise of each other. Medium's lead held on all 42 problems, 37% against 28% at xhigh, although xhigh fully repaired slightly more, 24 of 84 trials against 22.

Gemini 4 Hydrogen shows the opposite. Low and medium reached just 17%, while high (26%) matched xhigh (25%).

Carbon's best setting rests on two problems. Gemini 4 Carbon did best at low effort, 32%, mostly thanks to two problems it fully repaired in both trials. Its median recovery was 9%, close to the 7% at high, its top setting.

Sol is best at xhigh, but only just. GPT-6.2 Sol reached 50% at xhigh, 49% at low and 35% at medium.

GPT-6.1 Terra is the one model that improved step by step, 26% at low, 32% at medium and 35% at high, with xhigh at 30%. It used the full 25 minutes at every setting, and the steps are about the size of the noise.

Sonnet gains from effort, probably by working longer. Claude Sonnet 5.5 went from 12% at low and medium to 20% at high and 24% at xhigh, though none of its 72 trials reached 75%. At low and medium it stopped after 7 to 10 minutes, against 15 to 18 at high and xhigh.

Claude Opus 5.5 shows no such effect. Low (28%), high (29%) and xhigh (27%) are within two points, although at low it stopped after a median of 11 minutes against 18 at xhigh. Medium came out lowest at 23%, but its two runs scored 18% and 28%, further apart than any two effort levels.

Overall, the effect of reasoning effort is inconsistent and varies across models.

Takeaways

What it means

The best agents can already do real weight-space programming, but within a 25-minute budget most of them fully repair only a minority of the problems. Locating the bugs is the part they already do well, and most of the gap between models comes from what happens after that. The runs that succeed make an exact structural repair rather than a workaround, check each edit against the unedited network, and use all of the time they are given. None of that requires a new capability. It is method.

Limitations

Harness. Each provider's models ran in its own harness, so part of the gap may come from the harness. On the nine ablation problems, Opus 5.5 scored about the same in Codex as in Claude Code (27.9% against 26.7%), and Neon in Codex as in Antigravity (30.4% against 25.4%, one fully repaired trial apart). Opus also stopped early in Codex, so the early stop comes from the model.

Scope. The bugs come from one family, structural ones, designed by an agent that may favour some kinds over others, and the networks have at most 230 million parameters.

Trials. Most results rest on two trials per problem, so small differences between models or ablation settings may be noise.

What next

This is the first version of Bench the Weights. It covers 42 networks and one family of bugs. Next we plan to add more tasks and networks, and new kinds of bugs.

Help us grow the benchmark. If you have a network and a bug that pass the three tests, send them to us and we will add them, with credit to you. Submit a problem.

Everything will be open by 8 December. With this post, on 24 November, we open-source the harness and the prompts we used, on GitHub. On 1 December we release the bug-injection pipeline, so anyone can build new problems the way we built ours, and on 8 December the 42 problems themselves. The leaderboard will track new models as they are evaluated.

Until then, we can run your model. Send us a model and we will run it with the same harness, budget and problems as in this post, and share the results with you. Request an evaluation.

Coding agents have become really good at working with software. We see weight-space programming as a natural next step: enabling agents to understand, modify and repair the learned behaviour of neural networks. Bench the Weights is a first step toward measuring this capability, and we hope it will help push the field toward agents that can work directly on the models themselves.
